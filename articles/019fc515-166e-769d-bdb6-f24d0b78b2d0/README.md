## `strictNullChecks`有効化

`strictNullChecks`有効化は、コードに本来存在する契約や状態モデルを復元する作業といえます。

`strictNullChecks: false`下では、すべての引数・すべてのメンバが`null`、`undefined`を許容しています。`null`を確認せずにアクセスしている箇所がある場合、「実際にはその地点で非nullであるが、型に状態遷移が表現されていない」「本当に`null`が到達可能で、従来コードに考慮漏れがある」の2種類に分ける必要があります。前者について機械的に`| null`を明示の上non-nullアサーションで処理するのは何の解決にもなっていないので論外として、`if (this.member != null) this.member.doSomething();`とするのも、場合によってはnon-nullアサーションより問題があります。正常に起こり得る`null`、初期化順序やライフサイクルのバグ、到達してはいけない不正状態を区別することができなくなるためです。

望ましい対応は、`null`でない事実を、その事実が成立する地点から型として伝播させることです。いくつかパターンが見えてきました。setterなどで段階的に初期化することに由来するnullableは、コンストラクタや静的ファクトリから一度に注入するように寄せたり、set後のオブジェクトをnon-nullableフィールドを持つ別のオブジェクトとして返す。再初期化はクローンに、visitやmapは判定をコールバックに伝播させられる構造に書き換える。ステートマシンは機構をオブジェクトにするのではなく、状態を戻り値で取り回す。バリデーションを最外端まではじき出す。結果的に、判別可能ユニオン型の多用、集合指向、イミュータブル指向といった、TypeScriptイディオムの導入を伴うことになります。特定の構文（典型は`class`）を意図して避けるというより、TypeScriptの型システムが扱いにくい選択肢は自然に外れていくという形です。
